## RQ-5 — Noise Gate

### Question
The Web Audio API has no native noise-gate `AudioNode`. What's a reasonably simple way to implement one?

### Affected task IDs
Future **Noise Gate node** task (Fast-Follow sketch item in `plan.md` § Fast-Follow, listed as "pending RQ-5"). Non-blocking on Core MVP — Core MVP's 6 node types (Gain, Compressor, EQ, Delay, Reverb, Limiter) all ship using native `GainNode` / `DynamicsCompressorNode` / `BiquadFilterNode` / `DelayNode` / `ConvolverNode` and do not depend on this resolving.

### Constraints & evaluation criteria
- **Build-fast**: the whole app is scoped as a single-page, dependency-light static site (per `plan.md` DEL-1: "plain JS or minimal bundler", no framework, no backend). Core MVP currently uses zero third-party audio libraries — every node factory wraps a native `AudioNode` directly.
- **Lower priority**: Fast-Follow, sequenced strictly after Core MVP M6 ships and is validated live.
- **Comparison baseline**: every other node type in this app (Gain, Compressor, EQ, Delay, Reverb, Limiter) is a thin factory around one or two native nodes with parameter mapping — effort is small, no custom DSP, no new runtime concepts.
- **Must fit the existing reconnect/graph model** (AE-2/AE-4): whatever implementation is chosen has to behave as a normal node in the ordered chain — same lifecycle, same `connect`/`disconnect` semantics — so it can be dragged, reordered, bypassed like any other node.

### Options considered

**(a) Custom `AudioWorkletNode` computing running RMS/peak level + gain reduction below threshold.**
This is the standard, spec-recommended approach for any custom real-time DSP in Web Audio today. Per MDN's own AudioWorklet guide, the pattern is: define an `AudioWorkletProcessor` subclass, implement `process(inputs, outputs, parameters)` (called on the audio rendering thread, not the main thread, in fixed blocks — 128 frames per call unless otherwise negotiated), register it with `registerProcessor()`, load it into the context with `audioContext.audioWorklet.addModule()` (async — must await before instantiating), then create the node with `new AudioWorkletNode(context, name)`. Threshold/ratio/attack/release map cleanly onto `AudioParam`s via `parameterDescriptors` (a-rate for sample-accurate automation, k-rate for cheaper block-rate params — attack/release/hold are naturally k-rate). A minimal gate is genuinely simple DSP: track a running envelope (RMS or peak with a smoothing coefficient), compare in dB to a threshold, and either hard-mute or apply a smoothed gain-reduction curve below it, with hysteresis (separate open/close thresholds or a hold time) to avoid rapid chattering on sustained vocal transients. MDN's guide itself sketches a ~30-line noise-gate-shaped `process()` skeleton (per-sample dB comparison + gain-reduction formula), confirming the core algorithm is not exotic.
Real-world confirmation this pattern is production-viable: current (2026) browser-side voice-processing practice combines an `AudioWorkletProcessor` host with a denoiser (commonly RNNoise, WASM-compiled) plus a hysteresis noise gate on top, reporting ~13ms added processing latency at 48kHz — well under the ~100ms perceptibility threshold. A gate alone (no ML denoiser) is a small fraction of that cost.
Gotchas worth flagging for the eventual task: (1) Chrome's non-conformant `process()` return-value handling means `process()` must always `return true` or Chrome will not keep calling it; (2) no DOM/network access and no blocking calls inside `process()` — must precompute everything and use `MessagePort` for any main-thread communication; (3) allocation-free steady-state code is important to avoid GC-induced audio glitches.

**(b) `ScriptProcessorNode`.** Confirmed deprecated. MDN marks `ScriptProcessorNode` (and `BaseAudioContext.createScriptProcessor()`) as deprecated in the current spec, explicitly pointing to `AudioWorkletNode` as the replacement. The deprecation is not cosmetic: `ScriptProcessorNode` runs user code as an event handler back on the **main thread**, which (a) adds scheduling latency/jitter because it's competing with layout, GC, and other main-thread work, and (b) directly threatens this app's UI (drag-and-drop reordering, parameter sliders) — any main-thread jank stalls audio processing and vice versa. Multiple widely-used libraries (wavesurfer.js, RecordRTC) carry open issues specifically about migrating away from it because browsers now emit deprecation warnings/errors for it. **Recommendation: do not use it**, even though it would technically be "simpler" (synchronous, no separate module file) — it actively fights the app's live-reorder UX and the deprecation risk (removal is plausible on a multi-year time horizon) makes it a bad investment for a "build fast but not throwaway" project.

**(c) Existing libraries.**
- **`@sapphi-red/web-noise-suppressor`** (github.com/sapphi-red/web-noise-suppressor, npm `@sapphi-red/web-noise-suppressor`) ships a `NoiseGateWorkletNode` alongside RNNoise/Speex/GTCRN denoiser worklets, MIT-licensed, requires AudioWorklet. **Actively maintained**: latest release v0.4.0 published 2026-08-09 (12 days before this research), repo last pushed 2026-08-12, 87 stars, 3 open issues. This is a real, current, small, drop-in option — worth prototyping directly rather than writing from scratch, since it already handles the AudioWorklet plumbing and exposes a gate specifically (not bundled with a heavier denoiser you'd have to opt out of).
- **`noise-gate` (npm, github.com/tennisonchan/noise-gate)** — per its own description, "simply a compressor and a filter with pre-adjusted values," i.e., not actually gate DSP, just a preset wrapper around `DynamicsCompressorNode` + filter. Low value here since the app already has a first-class Compressor node; this doesn't provide new capability.
- **`rse/audio-node-suite`** exposes an `AudioNodeGate` (dB-threshold volume drain). Small, less prominent (fewer stars/visibility than sapphi-red's), not separately verified for currency in this pass.
- **Tone.js `Tone.Gate`** (tonejs.github.io/docs) — passes signal through only above a threshold, built on `Tone.Follower` for envelope tracking; documented as a common way to implement a noise gate. Tone.js is a large, general audio framework, not a single node — pulling it in only for this one feature would be a heavier dependency than the "build fast," native-nodes-only pattern the rest of the app follows.
- **Spec-level confirmation there's no first-party plan for this**: `WebAudio/web-audio-api` GitHub issue #2395 ("A NoiseGate/Expander node would be a good addition to the API") was filed in 2013, remains **open**, and is labeled "Needs Discussion," "Priority: Eventually," "size: L" — i.e., the spec authors themselves consider a native gate a nice-to-have that has not been prioritized in 13 years. No native node is coming; a custom/adapted worklet is the only path.

### Recommendation & rationale
Build a small custom `AudioWorkletProcessor` (RMS/peak envelope + threshold + attack/release smoothing + hysteresis), following the MDN pattern, OR adapt `@sapphi-red/web-noise-suppressor`'s `NoiseGateWorkletNode` directly (MIT license, actively maintained as of 2026-08-09, purpose-built, no heavier framework dependency). Either is compatible with the app's existing node-factory/registry pattern (AE-5..AE-10): it just needs `audioWorklet.addModule()` called once at startup and then behaves like any other node in `connect`/`disconnect` terms. Do not use `ScriptProcessorNode` under any circumstance. Do not pull in Tone.js just for this.

Given the app is desktop-only, single AudioWorklet nodes of this kind are cheap; CPU/latency risk is low relative to the reverb `ConvolverNode` already in Core MVP.

### Tradeoffs, risks, confidence
- **Tradeoff — build vs. adapt**: writing ~30-50 lines of custom worklet code gives full control over parameter naming/UX consistency with the rest of the node registry, at the cost of writing and tuning attack/release/hysteresis behavior yourself. Adapting `@sapphi-red/web-noise-suppressor`'s gate saves that tuning work but adds an external dependency (small, MIT, but still a dependency the "build fast, minimal deps" plan otherwise avoids) and its parameter surface may not map 1:1 to the app's generic parameter-control UI (UI-4) without an adapter.
- **Risk**: AudioWorklet requires an async module-load step (`addModule()`) before the node can be constructed — this is a different node-creation lifecycle than the other 6 node types (all synchronous native-node constructors). AE-4's reconnect engine and AE-2's graph-builder should be checked to confirm they can accommodate one async node-type constructor without a rework; this is a minor design wrinkle worth flagging to the future Noise Gate task, not a blocker.
- **Confidence**: High. Every claim above is corroborated by a primary source (MDN, GitHub API metadata, or the W3C spec-repo issue tracker) fetched on the research date.

### Implementation consequences
- The future Noise Gate task should be scoped as **Small-to-Medium**, not Small like Gain/EQ/Delay, and not Large — meaningfully more effort than a native-node wrapper (needs a new `.js` worklet module file, an `addModule()` bootstrap step, and either hand-written or adapted envelope-follower DSP) but well short of a "hard" project (no ML model, no WASM strictly required, no novel algorithm — attack/release gating is textbook DSP with working reference implementations to copy from).
- Recommend the task spec settle up front on build-vs-adapt (custom worklet vs. `@sapphi-red/web-noise-suppressor`) rather than leaving it open, since both are now concretely evidenced as viable; a quick prototype-and-listen comparison (per this app's own "sounds right" acceptance-criteria style used for Reverb/Compressor) is enough to decide.
- No change to Core MVP scope, milestones, or critical path — RQ-1 (reconnect engine) already has to support inserting arbitrary node types; a worklet-backed node is just one more node type registered the same way once AE-4 exists.

### Decision priority/status
**Priority: P2. Status: proposed — awaiting user approval.** Not committed by this research pass; this document is decision support for a future `plan-it-out` breakdown of the Fast-Follow phase.

## RQ-6 — Autotune / Real-Time Pitch Correction

### Question
Is real-time, in-browser "light" pitch correction ("autotune") feasible within reasonable effort? *(User explicitly flagged this as optional: "if it's too complex, not necessary.")*

### Affected task IDs
Future **Autotune feasibility spike / implementation** (Fast-Follow sketch item in `plan.md` § Fast-Follow: "Autotune feasibility spike and, if viable, implementation (pending RQ-6 go/no-go)"). Explicitly optional and non-blocking — Core MVP does not depend on this in any way.

### Constraints & evaluation criteria
- **Build-fast**, single-page static app, desktop-only, no backend, currently zero third-party audio-processing dependencies.
- **Explicitly optional** — the user has pre-authorized dropping this entirely if it's disproportionately complex. This changes the bar: it doesn't need to be "impossible" to get a no-go, just "not worth it relative to everything else in this app."
- **Comparison baseline**: same as RQ-5 — every shipped Core MVP effect is a native-node wrapper, effort measured in hours, not days. The Noise Gate (RQ-5) is already the single most complex node in the roadmap, requiring one custom AudioWorklet with well-understood, textbook DSP. Autotune is a qualitatively different tier of problem (real-time pitch **detection** + real-time pitch **shifting**, tuned together, on a monophonic vocal signal, at low enough latency to feel live).
- **Already-accepted risk baseline**: the app already accepts "baseline Web Audio latency... as a known risk" per its own constraints (plan.md/town-hall.md) — RQ-6(c) specifically asks whether pitch correction's added latency is *meaningfully worse* than that already-accepted baseline, not just nonzero.

### Options considered

**(a) Confirm no native pitch-shift node.** Confirmed via MDN's full list of built-in `AudioNode` interfaces (`GainNode`, `BiquadFilterNode`, `ConvolverNode`, `DelayNode`, `DynamicsCompressorNode`, `WaveShaperNode`, `IIRFilterNode`, `PannerNode`/`StereoPannerNode`, `AudioWorkletNode`, etc.) — no `PitchShiftNode` or equivalent exists in the spec. Any pitch shifting requires either a custom/library `AudioWorkletProcessor` or a delay-modulation trick (see Tone.js below).

**(b) Survey of approaches and current maintenance status:**

|---|---|---|---|

| **SoundTouchJS** (`cutterbl/SoundTouchJS`, npm `soundtouchjs` / `@soundtouchjs/audio-worklet`) | JS port of the C++ SoundTouch library; monorepo now ships `@soundtouchjs/core`, `@soundtouchjs/audio-worklet` (replaces deprecated ScriptProcessorNode), `@soundtouchjs/stretch-phase-vocoder`, `@soundtouchjs/phase-vocoder-worklet`, and a `@soundtouchjs/formant-correction-worklet` (LPC-based formant preservation specifically for vocals) | **Actively maintained**: repo `pushed_at` 2026-08-03, `updated_at` 2026-08-24 (i.e., updated within the last 2 days of this research), 307 stars, license MPL-2.0, only 1-5 open issues. Useful building block, not a full solution by itself. |

Autotune-style pitch **correction** (as opposed to generic pitch **shifting**) additionally requires: real-time pitch detection (to know the sung note), a scale/key quantizer (to know the target note), and then feeding a shift amount into the shifter every analysis frame — i.e., detection + shifting + a control loop, not a single library call. None of the surveyed libraries provide "autotune" as a packaged, drop-in feature; they provide the pitch-*shifting* primitive that a correction algorithm would be built on top of.

**(c) Latency/CPU realism.** Commercial real-time pitch-correction plugins (e.g., Antares Auto-Tune's dedicated "Low Latency Mode") report core processing latency around **2.5ms** — but that's a highly-optimized, purpose-built native DSP engine refined over decades, running as a DAW plugin with direct hardware audio I/O, not a browser WASM/JS pipeline layered on top of the browser's own audio-stack latency (buffer sizes, `getUserMedia` capture latency, output latency) that this app already budgets for and already accepts as a known risk. TD-PSOLA (time-domain) is characterized in the DSP literature as "simple and one of the fastest" pitch-shift techniques, favorable for real-time monophonic vocal use; phase-vocoder (frequency-domain) approaches are higher quality/more flexible but costlier per frame and traditionally associated with offline or generously-buffered use, though the actively-maintained SoundTouchJS and Signalsmith Stretch worklets are specifically engineered to make a real-time-viable version of this tradeoff. In-browser, a correction pipeline chains: mic capture latency + a pitch-detection analysis window (needs on the order of one pitch period, i.e. several milliseconds, to get a stable read on a fundamental — worse at low male vocal ranges, ~80-100Hz, where a period is ~10-12.5ms) + the shifter's own algorithmic latency + normal AudioContext output buffering. That analysis-window latency for reliable low-note detection is the piece with no equivalent anywhere else in this app's effect chain (Compressor/Limiter attack times are in the same ballpark but are single-stage, not chained with a second buffering stage). Realistically, this pipeline is likely to add a further tens-of-milliseconds on top of the app's already-accepted native-node latency — plausibly enough to be perceptible layered on top of an already-nonzero baseline, though this is an estimate pending an actual QA-4-style measurement, not a hard-measured number for this specific app's chain.

**(d) Go/no-go recommendation given "build fast" and "optional."**

**No-go for now (do not schedule for the next Fast-Follow pass); revisit only as an explicit, separately-scoped spike, and only if the user still wants it after seeing this writeup.**

Rationale: this is not "no native support so use a worklet" (RQ-5's shape) — it's "no library does the actual feature; you're assembling pitch detection + shifting + a quantizing control loop yourself, on top of a still-nontrivial pitch-shifting dependency." Even taking the best-evidenced building block (Signalsmith Stretch: MIT, most-starred, actively updated within 24 hours of this research, first-party real-time Web Audio support) as the shifting engine, "light autotune" still requires designing and tuning the correction logic (key/scale detection or manual key selection, retune speed, formant handling to avoid the "chipmunk" artifact on larger corrections) — a genuinely different scale of effort than any Core MVP node or even the Noise Gate. This is the kind of feature commercial products (Antares) have iterated on for over two decades. A rough, honest sizing: **Large** relative to every other node in this app, and probably Large in absolute terms too (low-single-digit days at best for something that sounds acceptable and doesn't glitch on a live signal; realistically more once you account for tuning attack/retune-speed against real vocal ranges and testing across the same browsers/hardware QA-2 already has to cover). Given the user has already pre-authorized dropping it if "too complex," and the honest sizing here is large relative to a project explicitly optimizing for building fast, the straightforward call is: **don't build it now.** If it's wanted later, treat it as its own standalone research-and-prototype spike (not a normal Fast-Follow task slot) with a hard time-box, using Signalsmith Stretch as the shifting engine and Pitchy (or an equivalent lightweight detector) for pitch tracking, and validate the "does the added latency feel bad" question empirically before committing further effort — don't guess it away in either direction based on this document alone.

### Recommendation & rationale
**Go/no-go: NO-GO for the next Fast-Follow pass.** Drop it from the near-term roadmap; keep it recorded as a possible future spike, not a scheduled task. The building blocks exist and are currently well-maintained (Signalsmith Stretch chiefly), so this is not "technically impossible" — but "light autotune" is a multi-part DSP+control-system feature that would consume disproportionate build-fast budget relative to a single-page app whose other 7 effects (6 Core MVP + Noise Gate) are each small, native-node or single-worklet tasks. This matches the user's own stated bar ("if it's too complex, not necessary").
